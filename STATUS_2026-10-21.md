## The finding: 030 §7b did not lock the functions down

030 §7b only ran `REVOKE ALL ... FROM PUBLIC` on five functions. Supabase grants EXECUTE on
new `public` functions to `anon` and `authenticated` **directly**, so revoking from `PUBLIC`
leaves those two grants in place. Supabase's own docs say so ("Database functions → Function
privileges": revoke from `PUBLIC` *and* from each role holding a direct grant).

- VERIFIED live (read-only query, rows pasted by Tommy): `anon_exec = true` on **all 25**
  SECURITY DEFINER functions in `rankedceo-waas`. `complete_onboarding`'s ACL shows it lost
  its `PUBLIC` grant but kept `anon=X` and `authenticated=X` — exactly the gap.
- VERIFIED live: `pg_default_acl` grants `anon`/`authenticated` EXECUTE on every future
  function in `public`.
- VERIFIED locally (throwaway Postgres): with those defaults, `anon` could rename another
  account by calling `update_company_info`. Four onboarding RPCs (`update_company_info`,
  `update_onboarding_step`, `skip_onboarding`, `update_preferences`) update
  `accounts WHERE id = p_account_id` with no ownership check. Only `complete_onboarding`
  checked the caller.

## 031 — written, proven locally, NOT applied (PR #319, draft)

`supabase/migrations/waas/031_harden_function_grants.sql`, idempotent, wrapped in a
transaction.

1. Default privileges: future functions created by `postgres` in `public` get no EXECUTE for
   `anon`/`authenticated`, and no global grant to `PUBLIC`.
2. Revokes EXECUTE from `PUBLIC` and `anon` on the 7 trigger functions, the 3 audit RPCs,
   the 6 account/conversation RPCs, the 5 onboarding RPCs, `get_current_user_id`,
   `get_current_user_account_id`, `get_active_commission_rate` and `assert_own_account`.
3. Re-grants to `authenticated` where a signed-in user calls it (including
   `get_current_user_account_id`, which RLS policies need) and to `service_role` for the
   audit RPCs.
4. Keeps `anon` on `resolve_tenant_by_hostname` only, because the code falls back to the anon
   key.
5. New `assert_own_account()`; the four onboarding RPCs derive the account from the JWT and
   refuse a mismatched `p_account_id`. `service_role` callers bypass the check.
6. Revokes `TRUNCATE`, `REFERENCES`, `TRIGGER` from `anon`/`authenticated` on all `public`
   tables and from the default table grant. RLS cannot gate `TRUNCATE`.
7. Functions are matched **by name**, not signature, because the live project has
   `handle_user_delete`, which 030 does not create; a missing function cannot abort it.

Deliberately untouched: the `handle_new_user()` body (belongs to the other product), and the
smile-assessment functions (`get_smile_account_id`, `get_smile_pool_account_id`,
`submit_smile_assessment_with_pool`). Nothing in this repo calls them. Note that
`submit_smile_assessment_with_pool` stays anon-executable and accepts `p_account_id`, so an
anon caller can write an assessment into any account. Flagged, not fixed.

Proof: `tmp/test_031.py`, throwaway Postgres, 030 then 031, **10/10 pass**. anon refused on
the onboarding RPCs; a signed-in user updates their own account; the same user is refused on
another account; an RLS policy using `get_current_user_account_id()` still returns only the
user's own rows; anon cannot `TRUNCATE`; the signup trigger still fires after its EXECUTE
grant is revoked; `resolve_tenant_by_hostname` still works for anon; `service_role` can act on
any account; 031 re-runs cleanly. `npm run check` exit 0. Not covered: real PostgREST JWT
plumbing — the service-role bypass reads `request.jwt.claims`, which PostgREST sets and the
harness sets by hand.

## The client-switch plan (PR #318, draft, docs only)

`docs/engineering/E3_CLIENT_SWITCH_PLAN.md`. Key points:

- READ: the CRM URL comes from `NEXT_PUBLIC_SUPABASE_URL` (17 files) and the service key from
  `SUPABASE_SERVICE_ROLE_KEY` (31 files); waas from `NEXT_PUBLIC_WAAS_SUPABASE_URL` /
  `WAAS_SUPABASE_SERVICE_ROLE_KEY`. If both pairs hold the waas values, the app works with
  **no code change** — the switch is an env change plus a redeploy, and rollback is the same
  in reverse. `NEXT_PUBLIC_*` is baked in at build time, so a redeploy is required both ways.

  logins. **D1 = A** (Tommy's choice): invite the 11 users into waas auth; each sets a new

  2, `calendly_connections` 1, `accounts` 6 (4 pool rows already seeded by 030). Counts must
  be re-verified the day of cutover.

  touching Production env), D4 (which Supabase URL Production admin code really uses —
