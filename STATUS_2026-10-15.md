## The A5 work (PR #297)

A5 from `docs/waas/IDEAL_AUDIT_AND_BUILDER_VISION.md` was the gap where the only
on-page/SEO signal in an audit was the PageSpeed "SEO" category — the site
scraper collected address and title hints for keyword generation only, never for
findings. A5 was chosen over A3 and A4 because it is **code-only and adds no new
running cost**.

The PR adds a new module,
`lib/waas/services/audit-engine/on-page-crawl.ts` (908 lines), which fetches the
homepage, selects up to seven internal targets (service and location slugs
prioritised), and fetches those plus `sitemap.xml` and `robots.txt` in parallel.
It emits findings for missing/oversized titles, missing/oversized meta
descriptions, missing or multiple H1s, missing canonical, `noindex`, missing
viewport, missing `lang`, missing JSON-LD (with local-business, service, and FAQ
variants), thin content, too few internal links, no service pages, no location
pages, missing sitemap, missing robots.txt, and `Disallow: /`. It also
aggregates per-page findings across the crawled set. It reuses the existing
regex primitives from `keyword-generator/site-scraper.ts` and `text-utils.ts`,
so no new dependency (no HTML parser) was introduced. Fetchers are injectable,
which is what the 14 new tests in `on-page-crawl.test.ts` rely on.

Scoring scope was confirmed as option A: a new `on_page` component at **10%**,
with the PageSpeed SEO category dropped from 15% to **5%** and relabelled
"Lighthouse SEO". The component weights still total 1.0, and the score-breakdown
UI iterates components generically, so only one emoji mapping needed adding
(`"Lighthouse SEO": "🔍"` in `app/audit/[auditId]/client.tsx`). Crawl findings
are surfaced through the existing `technical_issues` and `opportunities` arrays,
which the report UI and the PDF already render, so no report-layout change was
needed. The crawl is gated off in `mock` provider mode so offline/demo audits
make no network calls. `lib/waas/types.ts` gains the `AuditOnPage` shape and
four `on_page_*` provider-meta fields.
