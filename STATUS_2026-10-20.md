## The Supabase Preview failure — root cause and fix

`supabase db push` (run by the Supabase GitHub app) calls the CLI's
`FindPendingMigrations`, which merges two lists: the **remote** versions from
`SELECT version FROM supabase_migrations.schema_migrations ORDER BY version` (pure
**lexicographic** string order) and the **local** files from `fs.ReadDir` (full
**filename** order). When one version string is a **prefix** of another, the two orders
disagree and the CLI returns `ErrMissingLocal` = *"Remote migration versions not found in
local migrations directory."*

The offending pair was `0000085_baseline_forward_referenced_crm_tables.sql` (added in
#295) and `000008_fix_users_policies.sql`. The remote order is
`000007 → 000008 → 0000085 → 000009`, but the local filename order is
`000007 → 0000085 → 000008 → 000009` (because `'5'` = 0x35 sorts before `'_'` = 0x5F). One
inversion is enough to fail the whole push.

The fix renames `000008` → `0000080`, which removes the prefix pair (no version is a prefix
of another now) and makes the filename order equal the version order. The guard test
`lib/ci/migration-order.test.ts` rejects any future duplicate version, any prefix pair, or
any filename/version order mismatch.

Reproduced locally with `/workspace/tmp/sim_pending.py`, a verbatim port of the CLI merge:
before the rename the merge reports one missing version; after the rename it reports none.
Verified by the real hosted check: #313's Supabase Preview was green three times (a fresh
preview branch per PR has an empty remote history, so the merge is clean).

## `main`'s Supabase Preview is still red (new finding)

`main` HEAD `037968a` fails the Supabase Preview check in about 5 seconds with the *same*
message as before: *"Remote migration versions not found in local migrations directory."*
The check's `details_url` is `https://supabase.com/dashboard/project/wcednzaxmxwfiijzmjmx`
— i.e. on `push` to `main` the app runs against the **linked project** (the CRM project),
not a fresh preview branch.

The cause is now different from the original one, and it is **bookkeeping only**. The CRM
project's remote history still records the version `000008` from before the rename. After
the rename there is no local file with version `000008`, so the CLI reports it as a remote
version missing locally. The migration's *effects* are already applied; only the recorded
version string differs. Reproduced as CASE 2 in `sim_pending.py`: one missing version
(`000008`).

Consequence: `supabase db push` does not run on `main`, so a new migration is not
auto-applied to the CRM project (they have been applied by hand). `main` is not
branch-protected, so nothing is blocked — the check is noise that can hide real failures.

Fix (tomorrow), a remote-history repair on the CRM project. Read-only first:

```sql
select version from supabase_migrations.schema_migrations order by version;
```

If it lists `000008` and not `0000080`:

```sql
delete from supabase_migrations.schema_migrations where version = '000008';
insert into supabase_migrations.schema_migrations (version) values ('0000080');
```

Then re-run the check (push a trivial commit, or re-run the job). The equivalent CLI is
`supabase migration repair --status reverted 000008` followed by
`supabase migration repair --status applied 0000080`.

**Not verified:** I could not read the CRM project's `supabase_migrations.schema_migrations`
(no credentials). The `000008` entry is inferred from the identical error text plus the
local reproduction, not from a live query.
