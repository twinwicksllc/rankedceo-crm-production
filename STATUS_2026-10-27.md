## Finding 2: the rehearsal cleanup script deleted a real customer (VERIFIED)

`docs/engineering/checks/rehearsal_cleanup.sql`, written by a subagent. Its report said all its checks passed and its header said it refused real users.

- The agent's test harness was deleted, so the checks could not be rerun. I rebuilt a harness on a throwaway Postgres (PGlite) from the real `waas/000a` to `030` migrations, with `auth` and `storage` stubs.
- A real customer who signed up 5 days earlier, with one user, an account made at sign-up and a lead, lost both account and lead to a committed run. The preview showed only counts. The guards fit any recent customer.
- Fix: a committed delete needs `p_confirm_account`, the account id the preview prints, and the age window is 3 days. The plan's rule 1 no longer claims the age check protects a mistyped email.
- Checked: a customer 1 day old (inside the window) is refused without the id and with another account's id; a genuine rehearsal login is deleted with the right id; removing the confirmation, widening the window, loosening the id check, or removing the pool guard each fails a test. A control run on the unfixed script reproduced the bug.
- Not verified: the live `handle_user_delete()` body, live triggers and policies, and any behaviour on the project's Postgres version. The first live run must be a read-only preview.

## Lessons recorded as rules

- An agent's report and its own header are not evidence. Re-test a destructive script with a real-user-shaped row that sits inside every guard.
- When the same wrong name appears in code, search every place that parses or names it (the regex as well as the query).
- Do not tell Tommy to add a dashboard setting without checking what the code actually sends: my first redirect advice allowed every `vercel.app` address and then put the preview in the wrong place.
- Read what a flow does when a setting is on (Confirm email) before writing steps that assume it is off.
