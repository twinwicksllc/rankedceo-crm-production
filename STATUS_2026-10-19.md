## What the audits found

**Audit 1** (seven queries per project; the results are in the plan). The CRM project
already holds WaaS-style tables (`tenants`, `tenant_site_*`, `audits`, `client_*`,
`notification_log`) and the other product's tables (`ebay_*`, `listing_*`). The live
`get_current_user_account_id()` differs from the latest migration, so the repo migrations
are not the authority for the move. The live `on_auth_user_created` trigger on
`auth.users` in the CRM project belongs to the other product and is never edited.

**Audit 2** (18 queries). Key results, all now in the plan:

- The sign-up hazard is **confirmed**: the live WaaS `handle_new_user()` inserts only
  `accounts(name)` = `'My Account'` and `users(id, account_id, full_name, avatar_url)`,
  so any NOT NULL column without a default added to WaaS `accounts` or `users` would
  break every new WaaS sign-up.
- The live WaaS event trigger `rls_auto_enable` runs
  `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` on every new `public` table, so a new table
  needs its policies in the same change or it denies all access.
- The five onboarding RPCs are `SECURITY DEFINER` with `SET search_path TO 'public'` and
  take `p_account_id` with no ownership check. They write eleven `accounts` columns the
  WaaS table does not have yet.
- All 29 target tables have RLS enabled (29 of 29), so each needs its policies recreated.
- The CRM data is near-empty: the six WaaS-migration tables are empty, and of the 22 CRM
  tables only `agent_conversations` (31), `industry_leads` (5), `appointments` (2) and
  `calendly_connections` (1) have rows. CRM `accounts` has 6 rows, four of them pool
  rows, so only two are real customer accounts.
- `tenants.crm_account_id` has no foreign key, so the link from a tenant to a CRM account
  is by convention only.
