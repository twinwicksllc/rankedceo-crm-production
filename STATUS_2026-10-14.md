## #294 Copilot findings (8) — to fix tomorrow

Each is Copilot's claim as written. I have **not yet re-verified them against
the code**; that is the first step tomorrow. From reading the comments, all
eight look plausible.

1. `app/api/audit/[auditId]/create-tenant/route.ts:43` — public POST now reads
   any audit id with the service-role client and never checks token / owner /
   admin, so anyone with an id can create the tenant or fetch its `reviewToken`.
2. `app/api/audit/leads/route.ts:233` — public endpoint takes `audit_id`, and
   with the service-role client can overwrite the tenant's `brand_config.contact`
   and PDF counters. Needs authorization (pass the token from the email-capture
   form) or isolation of privileged writes.
3. `app/api/audit/run/route.ts:89` — the 24h cache hit is keyed only on public
   inputs, so a different requester repeating the same inputs gets a signed token
   for the earlier requester's report. Do not sign a cached audit for a new
   requester.
4. `app/api/audit/run/route.ts:153` — the route accepts `audit_id` from the body
   and signs it without an access check. Only sign newly created audits;
   authorize any existing-id rerun.
5. `app/api/waas/audits/[id]/status/route.ts:46` — completed/failed responses
   use `Cache-Control: public`; should be `private, no-store`.
6. `lib/waas/audit-access.ts:51` — a valid token bypasses the tenant and
   audit-type checks. D1=A allows token-only access only for an unlinked
   prospect: add `audit_type` to `AuditAccessRecord` and the status query,
   require `audit_type === "prospect" && tenant_id === null` in the token
   branch, and test linked and non-prospect rows.
7. `app/api/audit/run/route.ts:92` (and :155) — `poll_url` is returned without
   the token, so polling gets a 403. Append the token (after #3/#4 are fixed).
8. `app/audit/[auditId]/page.tsx:62` — password sign-in returns to the audit, but
   magic-link and Google go through a fixed `/audit/auth/confirm` that always
   forwards to `/audit/start`, so a matching-email addressee loses the report.
   Pass a validated local `redirectTo` through the callback.

### Why hold #294

Findings 1, 2, 3 and 4 are authorization gaps that the share-token design is
supposed to close. 1 and 2 are new in this PR: the routes moved from the anon
key (limited by RLS) to the service-role key without an added check. Merging
as-is could be worse than today for those routes. Dropping `audits_anon_read_own`
only makes sense once the code gate is correct.
